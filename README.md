# Triage

Triage is one decision inbox for scheduled jobs and for omp and dsh sessions. It shows one card at a time in priority order. Ask cards show the STAR situation, task, action, and result with options suited to the situation. Skip and later are built in.

## Agent sessions

Triage polls tmux once a second and reads each omp pane's transcript when its title changes to asking. Omp 18.18.7 uses `ask.arguments.html` and returns `details.answers` in form order. Triage converts supported radios, single selects, lone checkboxes, and text fields into native cards, then answers through field controls. Multi-select and multi-checkbox controls stay read-only and must be answered in the pane. Legacy `ask.arguments.questions` and `details.selectedOptions` remain supported. Agents need no triage-side code or plugin.

A reply keeps one card when tmux restarts and omp resumes it under a new pane id: a reply already dealt with stays handled, and a reply whose card is still queued from the old pane moves to the new pane. The tracker trusts a pane's omp breadcrumb only when it was written after the pane's pty appeared, or when the pane's omp was started with `--resume` or `--restore` of that session.
The inbox holds cards that need a decision. An omp run that stops earns an information card. omp shows the same waiting title for a finished run, an interrupted one, and one waiting on background jobs. Triage reads the last assistant message's stop reason. A finished reply earns a card, while errors earn a `Stopped with error` card with an error label and interrupts earn none. A run whose last message is a tool call, whose working row shows a background-job wait or automatic retry, or whose reply comes before a delivered background-job result or supervised-process exit has not stopped yet. Its card comes when it does. omp redraws the working row on every spinner tick. Triage reads three captures before queuing a card. omp drops the wait row when a background job finishes, seconds before the result reaches the transcript. A reply last seen with the row stays held until the transcript changes or 30 seconds pass without the row. A reply counts as a final report when its first line is a status line such as `ENVOY_STATUS: complete`, `ENVOY_STATUS: agent-done`, or `ENVOY_STATUS: incomplete`. Bold, code ticks or a heading mark around that line still count, and text after the status word on the same line starts the report. Every triage brief requires one. Every brief tells the session to finish every step its instructions allow, such as the checks, commit, push or deploy, before it reports. It then asks for a caveman-style STAR report, one short sentence each: `S:` the situation the card described, `T:` the task the brief set, `A:` what the session changed, and `R:` the outcome and evidence from finished work only. Each still-open action item gets its own `Remaining:` line after `R:`. The line names the action and what holds it. Reports with no open items write `Remaining: none`. The `R:` line becomes the card title. The report ends in a `Recommended action:` line. Non-investigation `complete` reports write `Recommended action: none`; investigations may name one evidence-backed next action. An `agent-done` or `incomplete` report may name one remaining item the session can carry out once Nick approves it, such as a change a standing rule reserves for his approval. Reports with no qualifying action write `Recommended action: none`. A remaining item that only the user can do or that waits on a later event cannot be the recommended action. Never put unfinished requested work, another slice of the task, an optional improvement, or a guessed approval blocker there. Complete reports say the whole requested outcome shipped through the project's normal pipeline, pushed or deployed as required, and the full suite passed. An `agent-done` report names a blocked step, such as a push or deploy the session cannot make or a Nick-owned approval, and what blocks it. The full test gate is part of the work, which a report never hands back. A run that could not use the method its brief named reports `incomplete`. The final report is one sentence per STAR label and one `Remaining:` line per open item. It gives the situation, task, work done, finished outcome and evidence. The `R:` line becomes the card title. No brief lets a session ask for a send or tell the user how to open a draft. A direction from the user outranks the action and any skill's flow. A final report written before a background wait stays the card's report, and the closing reply follows it in the body. A reply without a status line also ends the run, unless omp will start the session's next turn itself. That is the case while the session owns a supervised process (omp `bash` with `name`) that was started without a readiness gate less than two hours ago, or that exited less than a minute ago and whose exit omp has not yet reported. It is also the case for up to 30 seconds after the transcript last changed while the session's goal is active. A server started with a readiness gate never holds a card. A final reply never waits. A reply that ends the run earns the same card showing its title line as the title and the reply as its body, where a STAR report titles the card from its `R:` line and any other reply from its first line. The card for a reply that opens with an unstated outcome reads `No final report` while its session owes a report and `Reply` once the session has reported. A card that owes a report asks its session for it. Within ten minutes of the card appearing, the daemon types a one-line request into the waiting pane or prompts the idle dsh session with it. The report that answers it replaces the card. A newer card of the same session replaces an older one still queued. Triage removes `Recommended action: none`, `Remaining: none` and empty labels. Reports with open `Remaining:` lines read `Step left open` when their status is `complete` or `agent-done`, and the lines stay in the report body under Result. Investigations' evidence-backed recommendations and qualifying `Recommended action:` steps from `agent-done` or `incomplete` execution reports move under Action. An `agent-done` report with `Recommended action: none` and no open remaining item reads `Done`. A non-investigation `complete` report with a recommendation and no open remaining item reads `Step left open`, and the recommendation moves under Action. Complete reports with neither read Complete. An investigation keeps Complete status when it recommends a next step without an open `Remaining:` line. Acknowledge stays the primary action. A report whose recommended step is open offers `Plan next step`, which opens the session sheet preselected to Plan, beside `Do next step`, which opens it preselected to Act. An omp report runs either option in a window of its own, leaving the finished pane untouched. A dsh report continues its own session with either option, as every other dispatch from a dsh card does. Triage types into a finished session only to request a final report. A reply without a status line can show both `Plan next step` and `Request final report`. Carried replies follow the same status and launch-mode rule. Ended-session warnings and ingested `triage.info` bodies still move steps under Action. Finding cards show their Action and options. Ask cards show their choices. Plan cards show their proposals. Error cards keep their diagnostic text.
omp drops the background-job wait row when the job finishes, seconds before its result reaches the transcript. Triage holds any reply last seen with that row for up to 30 seconds while the transcript stays unchanged.
Resuming a session in its pane closes its queued and deferred report cards as `resumed in pane` when its title changes from waiting to working or asking. If the pane stays waiting but its transcript gains a reply, triage replaces the older card with the new one.

A session owes one final report for each brief triage sends it. A session started outside triage owes one in total. While a session owes a report, the inbox asks for a missing status line or an empty status-only report once its pane or dsh session is idle. After the session has reported, a reply without a status line answers a message the user typed. Its card reads `Reply` and triage leaves the session alone. `Request final report` stays on the card for a report on demand. In omp the transcript shows what a session owes. The report is due from the latest brief, or approved plan that carries the status contract, until a reply with a status line and a report body follows. The dsh bridge leaves user messages out of its event list. A dsh session therefore owes a report until triage stores a report card for it after the latest brief.

The request is one line that names `report-format.md`. The daemon keeps that file beside the database. It holds the status contract and the STAR, `Remaining:` and `Recommended action:` rules, which lets a session started outside triage follow the format. The inbox retries a refusal caused by a busy session, a pane that is not waiting, or a non-empty editor after 30 seconds. One accepted or ambiguous request per session per ten minutes prevents prompt loops. Active goal rounds wait for their closing turn. Ended-session warnings keep Restore. A DSH goal-closing reply carries a valid report from the immediately preceding completed turn only when the closing turn also calls `update_goal` and the preceding turn is not itself a goal close.


When a pane disappears, its ask and plan cards close as `pane exited`, because they need the live pane. Its information cards close with them only when the pane vanished alone, as when you close its window by hand. Several panes vanishing in one poll, or a dead tmux server, leave information cards queued. Unread reports survive a tmux server death this way. When omp is gone from a pane, whether its window closed, omp crashed or quit, or tmux died, the daemon reads the session once and queues at most one card. A session dispatched from triage, through a brief or an approved plan that carries the status contract, gets a warning card titled `Unreported: <first line of the last reply>` when no final report followed its latest brief. An aborted turn the user interrupted raises no `Unreported:` card. Otherwise a final reply the daemon had not yet carded gets its normal card, an error gets `Stopped with error:`, and a run cut off mid-turn gets a warning titled `Ended mid-turn: <first line of the last message>`. Both warning cards offer Restore run, which opens a new window where `omp --restore` picks the session back up with its todos and context, as its transcript reference names it. Warning cards carry the last reply as body and the transcript as reference. A session the user ran directly that ended cleanly, and a pane he closed from one of its cards, add nothing.

A triage-launched omp pane that comes up at `Error: No model selected.` and writes no transcript is relaunched once. Triage opens a new window in the same session and cwd, runs the argv the pane started with, then kills the dead pane. Omp starts without a model when it cannot read `~/.omp/agent/agent.db` within its busy timeout, which host load causes. A second no-model start of the same command raises an error card titled `Launch failed twice: No model selected` and leaves that pane alone.

A triage-launched omp that exits by itself before it writes a session, with a `SQLITE_BUSY` crash in its own `~/.omp/logs` entry for that process, is relaunched in the same session and cwd after one, two, four and then eight seconds, each with up to 400 ms of jitter. The log entry is what makes the launch safe to repeat; a startup death with another error keeps the old silent behaviour. A launch that dies again after the fifth attempt raises an error card titled `Launch kept dying at startup: database is locked` carrying the command, so it can be started by hand once the host is idle. A bare `omp`, which is the operator's own launch, is never watched this way.

For replies from sessions triage launched, the card shows the title of the card whose answer last launched or briefed the pane, and Task shows that answer and its note, as in `Investigate first · Note: so what should i do?`. Follow-up reports keep the first card's title, and briefs built from them carry both.

Every card states its outcome in color above the title. A report with an open `Remaining:` line reads "Step left open" in amber, even when its recommendation is `none`; the remaining lines stay under Result. This rule applies to investigations too. A non-investigation `complete` report with a recommendation and no open remaining item also reads "Step left open" and moves the recommendation under Action. An `agent-done` report with `Recommended action: none` and no open remaining item reads "Done" in green. Other `complete` reports read "Complete" in green. An investigation may read Complete and keep its evidence-backed recommendation under Action when no open Remaining item exists. An `incomplete` report or a turn that stopped with an error reads "Incomplete" in red. An `Unreported:` card and an `Ended mid-turn:` card read "No final report" in amber. A reply whose first line is not a status line reads "No final report" in amber and gets asked for the report while its session owes one. After the session has reported, such a reply reads "Reply" in the ordinary text color while triage leaves its session alone. An ask or finding card reads "Waiting on you" in the ordinary text color. A producer card reads "Notice" the same way. A dsh turn that ended while plan mode was still on becomes a plan card instead, because it wrote a plan and stopped for approval; a dsh host too old to decide that plan reports it as a card whose head reads "Plan ready" in the ordinary text color. The title then leaves out its `Done:`, `Agent done:`, `Incomplete:`, `Unreported:` or `Plan ready:` prefix. History and context rows repeat the same outcome beside the kind while history rows keep the full title. A card stored before the daemon recorded the outcome reads it from the title. A report with no transcript reference counts as a producer's notice. A reply card without an `ENVOY_STATUS:` first line keeps `Acknowledge & close` as its primary action and adds `Request final report`. That button sends the one-line report request to the waiting pane or idle dsh session.



Every finding option opens the session sheet on Goal with the task its label implies. An option whose label starts with Investigate and names a fix preselects Fix; every other label selects Act. The sheet offers Mode, Task, Engine, Model and Thinking, plus Execution model and Execution effort for Plan into. Start launches with those choices. The sheet also takes one image by the Attach image button or a paste: PNG, JPEG, WebP or GIF up to 10 MB. The daemon saves it under `uploads/` beside the briefs and hands it to the engine the way that engine takes one. Omp gets an `@` reference in the goal objective, the plan message or the typed brief. Dsh gets an encoded attachment on its launch or prompt. A finding option answered from that sheet carries the image into its brief too.

Every card carries a context thread one click away: `t`, the Context control in the card dock, or Context on a history row. The thread shows the card's whole story — the dispatching finding, the launches, your steering notes, every report the session produced including superseded ones, and the producer's related cards — oldest first, with the card you opened marked as the anchor.

### Goal mode

Every new omp window triage opens for a brief through a dispatch, a finding answer or the compose sheet starts in goal mode. The objective is the brief's first line and its file path, with an instruction to read the whole brief, so the launch command stays short whatever the brief's size; tmux refuses a command longer than about 16 KiB. Each launch chooses one of Goal, Plan or Plan into as its mode, then one of Investigate, Fix, Act, Verify or Simplify as its task. Plan and Plan into start those modes instead. A plan dispatch also starts in plan mode. omp records the objective as the session's first user message, and the exit audit recognizes a triage dispatch by the brief path in it. A brief sent to a waiting source pane stays typed text and keeps that pane's modes, except Plan toggles its plan mode.

### Tasks

Each task adds its direction to the brief and changes nothing else. A typed note follows the task direction. A plain New session defaults to Fix and carries this direction:

> Do everything reasonably and think hard. Think ponytail: the smallest change that fully solves the task, with smart, efficient, effective and clean decisions.
>
> Investigate and fix the root cause permanently and generically, not just this one problem. Make sure you don't break anything and that this type of problem does not occur again.

The sheet offers Investigate, Fix, Act, Verify and Simplify. Investigate reports evidence without changing anything. Fix follows the root cause rule above. Act carries out the requested work. Verify checks the work and runs its test gate. Simplify reduces the work without changing its behavior.


### Plan mode

When a plan brief opens a new window, a unique per-run config overlay beside the brief starts omp in read-only plan mode. If the card's source pane is already waiting, triage checks its Plan status and sends `M-P` if needed. omp draws the status row only after it resolves the plan file and plan model, so triage polls the row for up to 2 seconds before it sends the brief. A toggle that never shows returns 422.

The tracker waits for a transcript `write` to `xd://propose` and the fullscreen Plan Review overlay. Once both appear, it queues an answerable `plan` card with the redacted plan as its body. The Execution model picker lists omp's `cycleOrder` roles, and Default keeps the role shown in the overlay. Choosing a role moves the slider with Left or Right, waits for the redraw, and checks the selected role before sending Enter. An unavailable role or clipped slider leaves the card queued. The execution model takes the role's own thinking level, because omp's Plan Review slider lists roles only. Refine requires a note; triage moves the `❯` onto `Refine plan` with Up or Down, checks the marked row before Enter, waits for the overlay to close with plan mode still on, then sends the note as steering text. Triage never presses Esc, because that cancels the review and leaves the highlighted row able to approve the plan instead. A new proposal supersedes the old card, and closing the overlay completes it. Every plan brief ends with a status contract because Approve can start a fresh session that sees only the plan. That session's final report then earns its Done card.
Plan and Plan into launches pass the brief's first non-empty line before the `@file` argument. The line is capped at 120 characters, keeping the task visible in OMP's session title without putting the full brief in the command.

### Plan into

Plan into works like envoy's OMP Plan into. A Plan into launch opens a new window running `omp --plan-yolo` with the brief as its prompt. The planner explores read-only and proposes a plan, omp approves that first proposal on its own, and the same session switches to the execution model to carry the plan out. No Plan Review overlay opens and no plan card reaches the inbox, so nobody reviews the plan before it runs; choose Plan when a plan needs a look first. The planner is the model the sheet or the dispatch names, else the daemon's `--model`, else omp's own default. The execution model goes to `--plan-yolo-into`, and when none is chosen omp uses its `smol` role. It keeps the planner's thinking level unless its selector ends in `:<level>`, such as `provider/model:low`, or the launch names an Execution effort. Triage appends an Execution effort to the chosen selector as `:<level>`, or uses `@smol:<level>` when the selector stays at Default. A Plan into dispatch opens a new window even when the card's source pane is waiting, because only launch flags turn plan-yolo on. Its brief asks the planner to end the plan with the status contract, and the execution model's final report earns the normal Done card. The planner and execution fields also offer the configured omp roles as `@role` selectors, so a launch can plan on `@sol` and execute on `@smol`.

### dsh sessions

Triage can also launch sessions in dsh, DeepSeek's coding harness. `--engine dsh` makes dsh the daemon's default. The Engine picker in the session sheet chooses per launch. A dsh session runs in the dsh web host that `dsh-web.service` keeps running. Triage opens no tmux window for it. The daemon reaches the host through its loopback bridge, whose address and secret it reads from `~/.dsh/run/host.json` or from the file that `DSH_HOST_FILE` names.

A dsh session's model and thinking level come from dsh's own catalog. `GET /v1/models?engine=dsh` lists every model the host offers, with the default it gives a session that names none; the pickers offer exactly those selectors, and each model's declared reasoning efforts, so a level dsh would refuse is never offered. The daemon's `--model` applies only while the host still offers it, and otherwise the catalog default wins, which keeps a model that left the settings from reaching a launch. A launch with no choice sends no model, and the bridge selects the catalog default explicitly because every selection becomes dsh's saved default. Nothing in triage names a dsh provider.

Every new dsh session joins the workspace that `--dsh-workspace` names, `triage` by default, so the dsh web UI shows triage's sessions in one group instead of leaving each under Ungrouped. dsh groups a session by the directory it was created in, so a workspace session starts in that workspace's directory rather than the project's. Its brief therefore names the project directory and tells the session to call the `working_directory` tool with `cd` set to it before starting, and a dispatch brief carries the same directory under `## Working directory`. `--dsh-workspace ""` leaves each session in its own directory. A host older than workspaces refuses the launch, and triage then starts the session in the project directory, ungrouped, instead of failing.

dsh names a session from its first user message. A plan or plan-into launch records the brief prompt as one. Triage opens that prompt with the card's task, which gives dsh's title model the work itself instead of a brief path. Until the model answers, dsh's three-word fallback stands. A goal launch only creates a goal. Its rounds are not user messages, so dsh has nothing to name from there.

Triage names a goal launch itself, from the work the brief describes. It asks the host one judge question with the brief as its text, then pins the answer. A row reads `Fix blank login redirect` instead of `DIRECTION FROM THE USER`. The question runs in the `autorules` workspace, which the tracker skips. Triage archives the session that answered. A host that is down, slow or out of models leaves the brief's own task line, cut between words at 60 characters. That cut keeps every title inside the 80 bytes dsh keeps.

The effort reaches dsh unchanged, because each model declares its own ids: `deepseek-v4.1-flash` accepts `low`, `high` and `max`, and a model with no reasoning control takes no effort. The active host catalog also includes three `command-code` routes with no effort. `beam-free` accepts `low`, `medium`, `high`, `xhigh` and `max`. The host's own list appears when a model is no longer offered or the chosen model rejects its level.

A launch answers the inbox before the bridge does. Start waits two seconds, then answers `202` and leaves the launch running in the daemon for up to two minutes, so a host that is busy starting its first turn never holds the sheet or the phone. A launch that fails after that answer queues a `Could not start the session` card with the bridge's error and the prompt. A slow host is not a failed launch: dsh creates the session before its first command, so a launch that times out adopts the session it started. That is the one session listed in the launch's workspace directory after the launch began, plus the title when the launch sent one. Triage adopts a single matching session. Two matches leave the card on the timeout error instead. The card then points only at a session its launch started. A launch the bridge refuses names the session it created in that answer, and triage archives it before returning the error, so the retry leaves no duplicate behind it.

The tracker polls the bridge every 3 seconds and turns dsh questions, plan reviews and finished turns into the same ask, plan and report cards that omp sessions get. dsh answers `session/list` by projecting every session, which takes a second on a quiet host and ten on a busy one, so only `pending` decides whether the bridge is down: a failed or slow session list skips that poll and retries three seconds later, while a failed `pending` waits thirty seconds and prints the error once. A launch reads the session list only while adopting a session it may have started. A card's source is `dsh://session/<id>` with the label `dsh <session title>`. Peek on a dsh card shows the session's recent messages and tool calls. Send queues a prompt in an idle session, and a launch or prompt from the session sheet can carry an image, which the bridge hands to dsh as an encoded attachment, while Open brings up the dsh web UI on the desktop in place of Jump. Answering in the dsh web UI resolves the card as `answered in dsh`. A host restart resolves the open ask and plan cards as `dsh host restarted`, because dsh does not deliver a waiting question again. Answer multi-select questions in the dsh web UI.
A session whose `goalPhase` is `complete` reports its newest finished turn once the session cursor reaches that turn's end, even when the bridge still marks it `running`. Later events belong to the closing turn and hold the report until that turn ends.

A finished turn of a session still in plan mode earns a plan card instead of a done report, because that turn wrote a plan and no work ran. The card is titled `Plan ready: <plan heading>`, carries the plan as its body, and offers Approve and Refine like a plan review: Approve leaves plan mode with the Execution model and Execution effort, then starts the plan, while Refine sends the note back for more planning. Plan mode comes from the session's `planActive` field. Its plan card answers through the host's `POST /v1/plan`, which a host advertises as `planDecisions` on `GET /v1/sessions`; a host older than that route keeps the plan as a report card whose head reads "Plan ready", because it cannot leave plan mode for you. The turn after a plan card reports normally and supersedes it, and a session the host no longer lists closes its plan card, because nothing is left to approve. A turn that ends without a reply of its own earns no report card, because there is nothing to report. dsh ends a turn that way after an archive, so carding it would repeat the reply the user just closed.

Dispatch on a dsh card preselects the dsh engine and sends the brief to the card's session. A brief for Investigate, Fix, Act, Verify or Simplify waits in the dsh session, even while it runs or waits for an answer, because a prompt waits for the next turn. The work continues in the session the card came from. Plan and Plan into relaunch an idle session in that mode, since a plan changes its permission and plan mode between turns. A busy session for those two modes, a session the host no longer lists, and a prompt the bridge refuses start a new session instead. Plan next step and Do next step follow the same rule, because the `new_window` they ask for names a tmux window and a dsh card ignores it. A session state the bridge cannot read fails the dispatch and leaves the card queued, because the session may still be there. Close archives the session, stops its activity and resolves its cards. dsh finishes an archive even after its caller gives up, so Close waits 2 seconds for the answer, then resolves the card while dsh finishes. A refusal inside that wait keeps the card queued. Request final report prompts an idle session for its report. With Plan into, dsh-host approves the first plan itself and switches the session to the execution model, the way omp's `--plan-yolo` does.

A dsh launch names its Execution effort only beside the Execution model it changes, because dsh changes a reasoning effort along a model: a dsh sheet lists no effort level until an execution model is chosen, and its Default row then reads `needs an execution model`. Once a model is chosen, the picker lists the levels that model declares and follows it when the choice changes, and a level chosen for one model is dropped when the execution model returns to Default. dsh-host keeps the effort and applies it to the execution model when the plan is approved; an empty effort keeps the planner's effort. Approving a dsh plan card names both too: the Execution model and the Execution effort. An omp launch needs no model for an effort, which becomes the level of its default smol role.

## Event input

For `triage.finding`, `data` may contain `title`, `star` (an object with `situation`, `task`, `action`, and `result`), `options`, `questions`, `refs`, `cwd`, `org_id`, and `label`. Each option has a `label` and may have `description`, `direction`, and `recommended`. A finding question has `label`, `question`, `options`, and optional `allow_other` (default `true`); its answers are sent together in `answers[]`. A finding question may also carry its own `star`; triage shows that text on its step instead of the card's shared `star`, with `label` as the heading. The review step shows the card's shared `star` again. Triage presents each finding question's recommendation, then dispatches accepted Do or Other answers in Goal, Plan or Plan into mode with any task except Investigate. Skip and Keep do not launch. An all-Skip/Keep answer resolves without launching a session. Plain finding cards keep their existing option dispatch.


For `triage.info`, `data` may contain `title`, `body` and `level`. An emitter sends it only for a completed job. The daemon reads `refs` on a finding only, because the `refs` of an info card name the session transcript behind a report. Other event types are stored without a card.

| GET | `/app.js` | Serve embedded application script. |
| GET | `/marked.js` | Serve the embedded marked Markdown parser. |
| GET | `/sw.js` | Serve the service worker script with `no-cache`. |
| GET | `/manifest.webmanifest` | Serve the web app manifest. |
| GET | `/apple-touch-icon.png` | Serve the iOS home-screen icon. |
| GET | `/fonts/Geist-Variable.woff2`, `/fonts/GeistMono-Variable.woff2` | Serve the bundled fonts, cached for a year. |
| GET | `/v1/queue` | Return cards, ask/finding/info/plan counts, queue version, and `shell`, the ETag of the inbox files the daemon serves. |
| GET | `/v1/stream` | Stream queue version changes as server-sent `queue` events. |
| POST | `/v1/ingest` | Accept a CloudEvent and return `202` with `{ "ok": true, "stored": true }`. A `(source, id)` already stored returns `"stored": false`, still `202`. |
| POST | `/v1/cards/{id}/answer` | Answer a card using an option index, text, or note. Question findings accept one answer per question in `answers[]`; each answer selects an option or supplies permitted custom text. Skip and Keep resolve without launching. Other answers accept optional `mode` (`goal` by default, `plan` or `plan-into`) and `task` (the option label's implied task, or `act` for question answers). Question answers reject `investigate`. Unknown modes or tasks return 400 `unknown mode` or `unknown task`. The route also accepts `engine`, `model`, `thinking`, plan-into `executor` and `executor_thinking`, plus the same optional `image`. Plan approval may include `executor: "@role"`; it must match the visible Plan Review slider or approval returns 422. A dsh plan's `executor` is any selector dsh's catalog offers, and `executor_thinking` is one of that model's efforts, which dsh applies before approving. Invalid thinking levels or selectors return 400. |
| POST | `/v1/cards/{id}/skip` | Skip a card. |
| POST | `/v1/cards/{id}/later` | Defer a card with a `minutes` value. |
| POST | `/v1/cards/{id}/dispatch` | Hand a brief built from a card to an omp or dsh session. Optional `mode` is `goal` (default), `plan` or `plan-into`. Optional `task` is `investigate` (default, read-only), `fix`, `act`, `verify` or `simplify`; an unknown task returns 400 `unknown task`. An unknown mode returns 400 `unknown mode`. Optional `note` follows the task direction in the brief. Optional `model` (an omp selector or `@role`) and `thinking` (an `omp --thinking` level) override daemon launch choices for every mode. Optional `engine`, `omp` or `dsh`, picks the harness. A dsh `model` is any selector dsh's catalog offers. `executor` names the plan-into execution model (selector or `@role`) and `executor_thinking` its effort; both require `plan-into`. dsh requires `executor` when `executor_thinking` is set. For omp, an omitted `executor` applies the effort to its default `smol` role. An omp execution effort is appended to the selector as `:<level>`, and a selector that already names one keeps it. Invalid selectors or thinking levels return 400. An omp brief from an info card goes to its source pane while that pane waits for input. Every other omp brief starts in a new window with the selected launch choices. `new_window: true` always starts an omp window of its own, which the report card's next-step buttons ask for so a finished pane is left alone. A dsh card ignores `new_window`. A dsh brief goes to the card's session: a goal brief is queued there, and a plan or plan-into brief relaunches it while it is idle. A session the host no longer lists, a busy session for a plan, and a prompt the bridge refuses start a new session. A session state the bridge cannot read returns the bridge's error and starts nothing. The route resolves a finding or an info card with reason `launched <pane>`. It defers an ask or a plan card for an hour with reason `investigating <pane>`, `planning <pane>` or `acting <pane>`, because that card's dialog or review is still waiting for its answer. Optional `image` is `{media_type, data, name?}`, base64 of a PNG, JPEG, WebP or GIF up to 10 MB; an invalid image returns 400. |
| POST | `/v1/cards/{id}/report` | Ask the card's session for its required final report and resolve the card when the request is accepted. The card must be queued and `report_due` true. Omp panes must be waiting with an empty editor; dsh sessions must be idle. |
| POST | `/v1/cards/{id}/restore` | Open a new tmux window running `omp --restore` with the session id named by the card's transcript, so a crashed or killed run continues with its todos and context. The card must be a queued `exited:` card (`Unreported:` or `Ended mid-turn:`), including a reloaded copy. The window opens in the daemon's `--session` at the card's cwd. Failures return 422 and leave the card queued. |
| POST | `/v1/cards/{id}/reload` | Put a fresh copy of a handled card back in the queue. The copy gets the id `reload:<original id>:<uuid>` and the current time as its creation time; the original, its swipes and its history row stay untouched. Returns `{ok, card}` with the copy's id. 404 when the card is unknown; 409 when the card is queued or deferred, or when a copy of it is already queued. |
| POST | `/v1/sessions` | Launch an omp session from a free `prompt` in `cwd`, default the home directory, as a new window in tmux `session`, default the daemon's `--session` or `triage`. Optional `model` and `thinking` default to daemon flags or omp defaults; `mode` is `goal` (default), `plan` or `plan-into`. Optional `task` defaults to `fix` for a plain session or `investigate` when `note` makes the prompt context. With a note, the brief treats `prompt` as context and puts the note after the task direction. Without a note, the brief carries the selected task direction after the prompt. Plan into takes optional `executor` and `executor_thinking`; dsh requires `executor` when `executor_thinking` is set, while omp applies effort to its default `smol` role when `executor` is omitted. Unknown mode or task, invalid thinking or selector, or either executor field with another mode returns 400. Optional `image` rides the prompt the same way as a dispatch image, and an invalid image returns 400. Returns the new pane id. With `engine` set to `dsh`, dsh-host runs the session without a tmux window and the pane id is `dsh:<session id>`. A launch the engine has not finished after two seconds answers `202 { "ok": true, "starting": true }` instead, and keeps running in the daemon: the inbox never waits on a slow host, and a launch that fails after that answer queues a `Could not start the session` card carrying the error and the prompt. |
| GET | `/v1/tmux-sessions` | Return `{sessions, default, directories}`, the current tmux sessions the session sheet offers, the default one, and the distinct working directories of tmux panes, those most panes share first. |
| GET | `/v1/models?engine=NAME` | Return `{engine, models, execution_models, default, thinking, default_thinking}` for the engine the query names, `omp` or `dsh`, else for the daemon's `--engine`. Each entry has `{selector, name}`. For omp, `models` contains catalog-backed `@role` entries whose configured models are in the unfiltered `omp models --json` catalog, followed by the catalog rows that `enabledModels` allows. Roles on models outside the catalog, such as `@web` on `web/searxng`, are left out. `execution_models` lists configured catalog-backed roles from omp's Plan Review slider order. A failed model or cycle-order query is retried at the next 30-second check even when omp's config is unchanged. `default` and `default_thinking` come from daemon launch flags, or `null` when omp defaults apply. Both appear only when omp is the daemon's engine. For dsh, `models` and `execution_models` hold the live dsh catalog, each entry `{selector, name, efforts}`, where `efforts` lists the reasoning levels that model accepts. `thinking` holds dsh's fallback levels, and `default` is the catalog default, or the daemon's `--model` while the host still offers it. A host that cannot be read leaves the list empty and `default` null, so no picker offers a model dsh would refuse. The session sheet offers Engine, Model, Thinking, tmux session and directory pickers, while a card dispatch hides the last two and uses the card's own directory and the daemon's session. A model field offers the catalog of the engine its Engine field names. Choosing another engine empties that list until its catalog arrives, and the newest read is the one that fills it: a catalog that answers after the engine moved on never lands in the field, which a slow dsh bridge makes possible. |

| GET | `/v1/cards/{id}/context` | Return one card's context thread as `{anchor, items, truncated}`. Items are `{card, swipes}` rows, oldest first, carrying full cards with bodies and every swipe. ## CLI

- `triage serve [--listen 127.0.0.1:7340] [--db PATH] [--session NAME] [--engine omp|dsh] [--model SELECTOR] [--thinking LEVEL] [--dsh-workspace NAME] [--dsh-workspaces DIR] [--dsh-ignore-workspace NAME]... [--allow-host HOST]...` starts the server and pane tracker.
- `triage emit [FILE|-]` posts a CloudEvent from a JSON file or standard input.
- `triage finding --source URI --title T [--situation TEXT] [--task TEXT] [--action TEXT] [--result TEXT] [--option LABEL]... [--ref PATH]... [--org-id ID] [--cwd DIR] [--priority N] [--id ID]` posts a finding event.
- `deploy/finding-example.sh` shows a scheduled job posting a finding.

The client commands use `TRIAGE_URL` when set. Otherwise they connect to `http://127.0.0.1:7340`.

## Build and install

Build with `cargo build --release`, then copy `target/release/triage` to `~/.local/bin/triage`. Install `deploy/triage.service` as `~/.config/systemd/user/triage.service`, then run `systemctl --user enable --now triage.service`.

## Requirements

Triage needs Linux, tmux, and `omp` on `PATH`. The dsh engine also requires the dsh web host, which `dsh-web.service` runs. Building requires Rust 1.89 or newer, because the locked `uuid 1.28.0` declares `rust-version = "1.89"`. The test suite also needs Node.js, `curl`, `jq`, and `ss`.

## Configuration

Settings are `triage serve` flags; there is no configuration file. Put them on the `ExecStart` line of your copy of `deploy/triage.service`.

| Flag | Default | Effect |
| --- | --- | --- |
| `--listen` | `127.0.0.1:7340` | Address the daemon binds. Port `0` takes a free port. The daemon prints `triage: listening on ADDR` to stderr once it holds the port. |
| `--db` | `$XDG_DATA_HOME/triage/triage.db` or `~/.local/share/triage/triage.db` | SQLite database; briefs go in `briefs/` beside it, as does `report-format.md`. |
| `--session` | `triage` | tmux session new windows open in. The session must exist. |
| `--engine` | `omp` | Harness for launched sessions, `omp` or `dsh`. A request can override it in the session sheet, or on a finding answer. |
| `--model` | omp's own model | Default model for new windows. A request can override it in the session sheet, or on a finding answer. It takes an omp selector or `@role`; omp resolves a role when each window starts. A brief sent to a waiting source pane keeps that pane's model, except Plan mode can switch it to the pane's own `plan` role. With `--engine dsh` it takes any selector from dsh's catalog; empty takes the host's default. |
| `--thinking` | omp's own level | Thinking level for launched sessions; accepts `auto`, `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. A launch also names the level on its plan model, as `--plan=<selector>:<level>`, because plan mode runs the effort its own selector carries. A selector that already names a level keeps that one. |
| `--dsh-workspace` | `triage` | dsh workspace every new dsh session joins, so the dsh web UI groups triage's sessions. It is one lowercase name; dsh-host keeps the workspace in `~/.dsh/workspaces/<name>`. Empty starts each session in its project directory, ungrouped. |
| `--dsh-workspaces` | `~/.dsh/workspaces` | Directory dsh-host keeps one directory per workspace in, the dsh-host `--workspaces`. The ignored-workspace comparison uses it. |
| `--dsh-ignore-workspace` | `autorules` | Repeatable. dsh workspace whose sessions never become cards, because an automated producer runs there. An empty value tracks every workspace. A name equal to `--dsh-workspace` stops the daemon at startup. |
| `--allow-host` | none | Repeatable. Host names accepted besides `localhost`, `127.0.0.1` and `::1`. |

An invalid `--model` or `--thinking` stops the daemon at startup, for example `ExecStart=%h/.local/bin/triage serve --session work --model provider/model-id --thinking high --allow-host my-machine.my-tailnet.ts.net`. Client commands read `TRIAGE_URL`.

## Web inbox

The web UI is served at `/`. Its keys are the Emacs client's. `tests/emacs-keys.test.js` fails when the two clients' key tables differ. A card shortcut names an action, never a button position. One table in `ui/app.js` lists every card action with its key, its button label and the cards that offer it. The dock, the key handler and Enter all read that table. A card shows one button for each action it offers. Each button carries the key that runs its action. That key does nothing on a card that does not offer the action. A finding is not tied to a session and ignores `C`, `v` and `J`. Acknowledge is `a` and Acknowledge & close is `C` wherever each one appears. Enter runs the button the card marks primary. A report with an open recommended step keeps Plan next step primary. A report with a session and no open step keeps Acknowledge & close primary. Both still offer plain Acknowledge at `a`, which is the primary on an info card without a session. A prompt that takes its answer in its pane or in the dsh web UI is read-only in the inbox and keeps Peek primary. Enter on every other ask, plan or finding card picks the recommended option or, on a review step, sends the answers.
Digits choose an option. The digit after the last option opens Other. A finding option opens the session sheet on Goal with its implied task. `p` opens it preselected to Plan and Act. On a report card that offers Plan next step, `p` plans that step. `D` opens the sheet on Goal and Act for Do next step. Each option opens a new window for omp reports and continues the card's session on dsh reports. `o` opens Other text (submitting it empty keeps the field open and says to type an answer), `n` focuses the note, `d` opens the sheet with Investigate. `f` preselects Fix, `A` Act and `P` Plan into. `C` acknowledges a card and closes its session, which exits omp and closes the tmux pane or archives the dsh session. `r` requests the final report from a reply card that missed its status line. `R` restores the run of an `Unreported:` or `Ended mid-turn:` card in a new window. `s` skips, `l` opens Later, where `1` picks 1 hour, `4` picks 4 hours and `t` picks Tomorrow, `v` peeks at the card's pane or dsh session, `t` opens context and `J` jumps to the pane. A dsh card shows Open in place of Jump, where `J` opens the dsh web UI. `w` copies a reply. On a plan card, `e` opens the Execution model picker, and on a dsh plan card `E` opens Execution effort. `c` opens the session sheet for a new session, `h` opens history, `S` opens Settings, `g` refreshes, `j` and `k` move through cards, and `?` opens help. In Peek, `f` switches between Fit and Readable, `s` moves to the text to send, `g` refreshes and `J` jumps to the pane. In History, `t` opens the context and `r` reloads the card of the focused row. `g` refreshes History and Context. `q` closes Peek, History, Context, and the session sheet.
The session sheet has Mode and Task controls, Engine, Model and Thinking, plus Execution model and Execution effort for Plan into. Plan approval offers the same two execution fields on a dsh plan card. The sheet opens on the engine of the card's own session, which is dsh for a dsh card and omp for a card with a tmux pane. A plain session opens on the engine last picked in the sheet, which starts as the daemon's default. Every card has a Note field. The sheet's Instruction is that same note, which keeps its line breaks in the sheet and reads as one line on the card. Every sheet offers Goal, Plan and Plan into. A finding's answers hide Investigate from the Task control. A task never writes into the Instruction, and a typed note follows its direction. A card's context strip names its title and source, and Clear drops the card and leaves a plain new session. The plain session defaults to Fix. Dispatch defaults to Investigate. Plan and Plan into preselect Act. A card's sheet opens on its options and a new session's sheet opens in its text, as in Emacs. Outside a text field, `m` and `T` move into Mode and Task, where each button shows its key. The modes take `g`, `p` and `P` (`g` and `p` on dsh) and the tasks take `i`, `f`, `a`, `v` and `s`. `d`, `s`, `e`, `M`, `t`, `x` and `X` open the Working directory, tmux session, Engine, Model, Thinking, Execution model and Execution effort pickers whenever the sheet shows that field. `a` attaches an image, Ctrl+V pastes one anywhere in the sheet and `D` drops it. Tab moves from the options into the text. Ctrl+Enter or Start launches the session. Enter alone never does. A New session sheet keeps its text when it closes, until a session starts.
The sliders button in the top bar, or `S`, opens Settings, which holds the Dictation form. A microphone appears beside the card's Note, the Other answer, the text for the pane in Peek and the session sheet's text field whenever the browser offers speech recognition on a secure page, served over HTTPS or from localhost. A browser that can recognize speech on the device is told to do so: the inbox reads `SpeechRecognition` or `webkitSpeechRecognition`, takes the on-device path only when `available()` and `processLocally` exist, and sets `processLocally` on every recognition. Chrome 139 or later and Firefox 160 or later offer that on a desktop. Safari offers only `webkitSpeechRecognition`, which sends the audio to Apple's speech service, so the microphones work on iPhone, iPad and Safari through that service, and the Settings sheet says the words leave the device. iOS 14.5 or later also needs Dictation and Siri enabled in the device's Settings; a page cannot turn that on, and Safari reports no speech without it. Audio never reaches the daemon. The first press on a site sets up the browser's speech model for that site, which can take a few minutes. After that, a press starts listening and a second press stops it. Every recognition is continuous, so Safari 17 or later, Chrome and Firefox keep listening across short pauses. Safari before 17 still ends a run at the first pause; the run then finishes with the words it heard, and the next press starts it again. The page keeps one recogniser and reuses it for every run, because iPhone can ask for the microphone again for a new one. A recogniser that never reports starting is dropped, and a start or stop the browser never answers ends within seconds with a message instead of a microphone that answers no press. A hidden page drops the run, as WebKit refuses speech recognition while the page is not visible. The words go in at the cursor each time the browser finishes recognizing a stretch of speech, read by index from the array-like result list, which has no iterator. Each Dictionary line reads `heard = written`. The inbox matches the heard form as whole words in any letter case and puts the written form in its place. The daemon keeps the dictionary for all devices. `GET /v1/dictation` reads it and `POST /v1/dictation` saves it.
The top bar and the card share one centered column. The card head shows the card's place in the deck, such as `1 of 7`, beside a rail with one bar per waiting card in deck order. Higher-priority cards get taller bars, and the shown card's bar is blue. A higher-priority arrival moves the view to the deck's top card. An open Later menu or typed answer text on the shown card keeps it in place. Under the title, a row of facts gives the source, directory, pane, kind, priority and waiting time. From 1100px wide, the evidence (Situation, Plan, Task and Result) fills the left column and the Action options fill the right, so the answer stays beside what it answers. When the window is also at least 760px tall, the Action column stays in view while the evidence scrolls. Narrower screens stack the evidence above the Action block, which then sits next to the dock. Plan cards show their plan under Plan, and info cards show their final reply only under Result. Card text renders as Markdown. The evidence blocks and the final reply show headings, lists, tables, quotes, code blocks, emphasis and links, and titles and option text show code and emphasis without links. Raw HTML shows as literal text, only http, https and mailto links become links, each opens in a new tab, and a remote image in the text shows as a link instead of loading. A body that parses as JSON shows as one code block. The parser is marked, vendored as `ui/marked.js` with its MIT license in `ui/marked.LICENSE.md`, and the inbox builds the elements from its tokens, so card text never passes through `innerHTML`. When an ask's task repeats its title, the card has no separate Task block. Dock buttons show their action's key, as do header buttons on screens wider than 800px, and touch screens hide every key hint. On phones the facts drop their labels and run together under the source name, and the four counts fold into a single total that opens them. The text uses Geist and Geist Mono, and the daemon serves both fonts from `ui/fonts/`.
When a card action advances the inbox, the next card enters from the right. Answering a card below the top returns to the top-ranked card from the left.
For remote access, publish the server on a tailnet with `tailscale serve --bg --https=7340 http://127.0.0.1:7340`. That gives `https://<machine>.<tailnet>.ts.net:7340/` with a Tailscale certificate and tailnet-only reach. Start the daemon with `--allow-host <machine>.<tailnet>.ts.net` so it accepts that host name. The published port must match the `--listen` port or be the default HTTPS port. The server has no authentication of its own, so never expose it beyond the tailnet. `tailscale serve --https=7340 off` removes it.

On iPhone and iPad, connect the Tailscale app before opening the inbox. A `ts.net` name resolves only through Tailscale's DNS. Without the tunnel there is nothing to reach. iOS suspends the app in the background. Turning on Connect on Demand in the Tailscale app keeps it running. Some Safari settings reroute DNS around Tailscale. These include iCloud Private Relay, Limit IP Address Tracking, or an encrypted-DNS profile. With any of them on, the name fails to resolve even while the tunnel is up. Try the Home Screen icon first, since it is not a Safari tab and avoids those Safari-only settings.

## Scope and limits

The default address is `http://127.0.0.1:7340`. Triage understands two harnesses, omp in tmux panes and dsh through the dsh web host. Omp's native Plan Review overlay is the first signature in a generic screen-signature to card to keys relay. Claude Code's `--permission-mode plan` and other harnesses can use the same path as future signature rows, without new plumbing. Multi-select and multi-checkbox asks stay read-only in the inbox and must be answered in the pane. HTML asks support radios, single selects, lone checkboxes, and text fields. Multi-question asks are answered step by step. A `triage.finding` with native `questions` gets one answer per finding. A question with its own `star` shows only that finding on its step, while the review step returns to the card's shared content. Caller review and supplier prune keep one card per fire under a per-fire event ID. Autorules audits, Etsy ads audits and Upwork analysis post one plain finding card per finding. Question-level `allow_other` controls free-text answers. Finding answers dispatch in Goal, Plan or Plan into with any task except Investigate. Skip and Keep resolve without launching. A restored pane that gets the same pane id its reply had before keeps the old card id, which still blocks a re-queue. A report from a session omp resumed under a new pane id after a tmux restart, or one the exit audit queues after its pane is gone, has no Situation or Task. A pane that vanishes while the daemon is down is never audited, because the tracker's seen-set lives in memory.

## Known Issues

Two performance limits are known. Each poll tick scans and parses every open and deferred card under the database mutex, and the poller runs the full queue query twice per tick. Open behavior limits are the ones under Scope and limits.

## Emacs inbox

The Emacs client uses `j`/`k` or Left/Right to switch cards. After you answer a card, the next card takes its place. Repeated card switches reuse Markdown fontification.

Card actions use Magit-style mnemonic keys, and every dock button prints its key: `d` Dispatch, `D` Do next step, `f` Fix, `A` Act, `p` Plan, `P` Plan into, `a` Acknowledge, `C` Acknowledge & close, `r` Request final report, `R` Restore run, `s` Skip, `l` Later, `t` Context, `v` Peek, `J` Jump, `n` Note, `o` Other, `w` Copy reply. `?` lists every key on the shown card.
In a session sheet, `C-c C-c` launches from the option rows or the text. `RET` never launches.

`M-x triage-delegate` captures an Org heading or agenda entry, a notmuch thread, marked Dired files, or an active file region and opens it in a session sheet. The sheet starts in the context's directory on Goal and Fix. Its direction is empty. The launch goes through `/v1/sessions` with the direction as `note`. Org tasks name their attachment directory when one exists. A selected mail passage limits the task to that passage. The whole thread remains reference. `triage-delegate-omp` and `triage-delegate-dsh` preselect the engine. `triage-start-session` starts a prompt through `/v1/sessions` for unattended fallbacks such as mail unsubscribe.

Context capture widens narrowed Org buffers while it reads the task and restores the narrowing before it returns. Region prompts use the saved text and name the exact selected lines. A contextual launch asks before replacing a different unsent draft. Cancel hides a New session or context sheet and keeps its text for the next time it opens. A New session or context launch keeps the sheet open until the daemon answers. A failed launch leaves the text and options ready for another try. Repeated submits cannot start duplicate sessions.

`triage-clock-mode` clocks the Org heading `triage review` while you review cards. Set `triage-clock-heading` to `("~/Documents/orgstuff/master.org" "triage review")`, then turn the mode on. Review starts on the inbox, card context, peek, card Dispatch sheet or history when the selected window belongs to a focused frame and Emacs has seen input in the last five minutes. Every Triage screen keeps the clock going. A visit elsewhere shorter than a minute also keeps one logbook line; after a minute away, review stops at the last time it was seen and resumes the interrupted clock from there. Five minutes without input on a Triage screen stops review at the last key and leaves the earlier clock stopped. Clocks under a minute leave no logbook line. Leaving review opens no clock-out note.


New omp windows set `OMP_MCP_STARTUP_TIMEOUT_MS=0`, so the first turn waits for MCP servers before it uses their tools.

## Development

Run `cargo test --release`, `node --check ui/app.js && node --check ui/sw.js`, `TRIAGE_BIN="$PWD/target/release/triage" node --test tests/*.test.js`, `cargo build && tests/smoke.sh`, and `cargo clippy --release`. The smoke test uses `target/debug/triage` unless `TRIAGE_BIN` names another binary. The Rust unit tests of `cards`, `server` and `db` live beside their module in `src/<module>/tests.rs`.

The Emacs client lives in `emacs/`. With Emacs 30.1 or newer and dependencies under `ELPACA` listed in `emacs/Makefile` under `DEPS`, run `make -C emacs check`. Run `cargo build` first for daemon-backed ERT tests. Set `TRIAGE_BIN` to the absolute daemon path when needed.

To load changed Emacs files into a running Emacs, run `make -C emacs compile` and then `emacsclient --eval '(triage-reload)'`. A plain `load` keeps each Triage keymap as Emacs first defined it. A new key then stays unbound until Emacs restarts.
